Intentional adaptations:

- Email/password authentication has no Stitch screen. It uses Welcome imagery and shared fields/buttons. Account confirmation follows Supabase Auth settings.

The Stitch guest ranges map to representative planning counts (25, 75, 125, 200, 250) with a visible explanation. Wedding Date uses a native Android dialog and an iOS spinner sheet. - Stitch's optional target budget has no Wedding-wide creation field. It is explicitly labeled **preview only**, held only in the in-memory draft, and excluded from the RPC. Budget setup belongs to the later finance slice. The Stitch copy that claimed automatic saving was replaced with the true creation moment.
- Motif title and color swatches persist through authorized `wedding_motifs` and `motif_colors` access. The Stitch cover photograph is bundled as an editorial preview. Changing or uploading a cover through Attachment/Storage is deferred; this screen does not imply that the image was saved to the Wedding. The completion CTA advances to partner invitation because the Wedding dashboard is not in this UI slice. The example budget badge was omitted because there is no persisted target value.
- Invitation issuance targets the existing second Partner Person and opens the native/web share sheet with a one-time `katipan:///accept-invitation?token=...` link. The receiving route is a small Warm Editorial adaptation needed for that link to resolve and uses the existing `accept_wedding_invitation` RPC. The raw token is never logged or saved to local or database storage. Pending state stores only invitation metadata. Stitch's channel-specific Messenger/Viber buttons are replaced by the platform share sheet.
- Stitch's entry for joining an existing invited workspace on Create Our Wedding is deferred to the receiving invitation route. Partner invitation can be skipped; the planning dashboard will be the next UI slice.

## Physical-device follow-up — 2026-09-27

The reported Android findings were addressed as follows:

- Signup and invitation signup now pass `katipan://auth/callback` as `emailRedirectTo`. Supabase JS uses PKCE; its verifier is persisted by the existing native Expo SecureStore adapter. `/auth/callback` exchanges the one-time code, confirms a persisted session, and routes through the authenticated root flow. Invalid, reused, or expired callbacks offer a safe route back to sign in without displaying or logging callback credentials.
- In the existing motif migration, authenticated users may insert `wedding_motifs.wedding_id`, but UPDATE is intentionally limited to `title`, `description`, and `notes`. The previous PostgREST `upsert(... onConflict: "wedding_id")` attempted a conflict UPDATE that also wrote `wedding_id`, which violates that column grant. The client now performs a read followed by an insert or a title-only update, then replaces colors. This respects the existing Owner/Full Coordinator RLS contract and requires no migration. Development builds show only the failed operation stage; user-facing errors contain no database details.
- The native date selection returns local calendar components as `YYYY-MM-DD`; formatting anchors those components in UTC so display cannot shift the selected day across time zones. Selecting “We haven’t chosen a date yet” clears the draft date and submission omits it.

Supabase Auth URL Configuration must include `katipan://auth/callback` under **Additional Redirect URLs**. Keep **Site URL** set to the deployed web origin. Add `http://localhost:8081/auth/callback` (or the actual Expo web development origin) only for web development, plus any deployed web callback origin used by the web app. The app's Expo config already declares the `katipan` scheme. Stable email-confirmation deep links require an installed development or production build; Expo Go is not the final deep-link test target.

The database cause was checked against live DEV grants, RLS policies, the generated database contract, and the existing migration. A throwaway `.invalid` Auth identity was created without sending mail, but the project's Auth API rejected that database-seeded identity at password sign-in. It was deleted immediately and no Wedding was created, so an authenticated owner API replay and reload could not be completed in this session. The client behavior is covered by mocked operation-stage and round-trip tests; physical-device confirmation still requires a development build configured with the project publishable key.

DEV migrations match the 19 repository migration versions. The relevant typed RPC signatures and authorized motif tables match DEV. No schema change was needed. A rollback-only authenticated DEV smoke transaction created a couple Wedding and issued a Partner invitation, verified all returned IDs, and left zero smoke Weddings afterward. It did not create a lasting Auth user or send an external invitation.
